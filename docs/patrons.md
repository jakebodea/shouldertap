# Free core and optional patrons

Implementation as of October 21, 2026. **Patron support belongs to the person sending taps.** The sender pays to customize the taps they send; recipients never pay to see them. This replaced a same-day receiver-owned theme model (recipient paid to theme their own screens), which was deployed only to the isolated `patron-sandbox` stage. The integrated sender model is now deployed only to `patron-sandbox` from application commit `4e13119` on `t3/sustainable-free-business-model`. A new actual test checkout verified sender billing, cross-pairing styles, cancellation, refund and provider replay; see [hosted sender verification](verification/sender-themes/hosted-sandbox.md). Older receiver-model purchases below remain historical evidence and do not prove sender billing.

Core sending, receiving, replies, pairing and recipient controls are free. The existing safety limits remain: 30 taps per sender per rolling hour, 20 active senders and 10 active devices per inbox. No limit depends on payment.

Optional support costs **US$24/year**, described as **$2/month, billed $24 annually**, plus applicable tax. It renews annually until canceled. While it is active, the taps the patron sends can use a theme (Broadsheet, Billboard, Terminal, Note), to every person they're paired with, with no per-recipient fee or recipient cap. It never unlocks messaging, delivery, replies, recipient controls or the Default look, does not promise future themes or permanent ownership, and is not a tax-deductible donation. There are no third-party ads, sponsors, watermarks, badges or business tier.

## Sender themes

- **Who sees what.** Every tap carries the theme its sender chose, captured by the server when it accepted the tap (`taps.theme`, CHECK-constrained to `TAP_THEMES`, null on older taps = Default). Recipients see each sender's own theme, so two senders can arrive in two styles. Free recipients see a patron's theme; a recipient's own billing plays no part.
- **Recipient control, free.** `appearance.senderThemes` (`show` | `plain`, default `show`) and `appearance.motion` (`system` | `reduced`) are per inbox, shared by its computers, saved with `PUT /v1/appearance` by any device, never gated. `plain` draws every tap in Default; reduced motion (the OS setting or "Always reduce") is the 160ms calm fade for every theme. Neither changes delivery, controls, keyboard shortcuts, the queue, multi-display behavior or replies. All eight colors and accessibility are free.
- **Sending.** `SendTapRequest` gains optional `theme` and `patronKey`. The Worker turns them into a `VerifiedTheme` (`apps/server/src/presentation.ts`) by asking the sender's SenderPatron whether that key is an active patron right now; the Inbox's `sendTap` accepts only that type and never sees the request's theme or key. Default, a missing/malformed/forged/revoked key, a lapsed, paused or refunded membership all store **Default and still deliver** the tap; the response's `theme` tells the sender what was stored and the web composer says "Sent in Default". The server never accepts CSS, HTML, fonts or assets from a sender: only a known theme name, rendered by each client's own native composition.
- **Lapse and refunds.** Entitlement is checked at send time. A tap already accepted keeps its theme for its whole life (queue, history, retries with the same request id), even if the membership later lapses, is canceled or refunded: it was sent while entitled, and rewriting someone's queued messages would be surprising. New taps after a lapse are stored in Default. Clients don't re-check entitlement; they draw what the tap says.
- **Compatibility.** Old servers omit `theme`; old clients ignore it (they show Default). Clients decode an unknown theme name as Default: TypeScript `KnownTapTheme`, Swift `TapTheme(from:)`, Rust `TapTheme::deserialize`. Old sender clients and outboxes send no theme and keep working; persisted web outbox items without a theme send in Default. The receiver-experiment fields `theme`/`shownTheme`/`canChooseTheme` are no longer emitted; current clients ignore them if a sandbox server still sends them, and that experiment's saved `appearance.theme` column is retained but unused. `scripts/check-protocol-sync.ts` fails if `TAP_THEMES` or `SENDER_THEME_PREFERENCES` drift between TypeScript, Swift and Rust.
- **Surfaces.** Web sender: **Style** under the composer opens `/style`, with live previews of all five compositions (ported from the approved sketches in `apps/web/src/components/tap-preview`, Broadsheet with only message, sender, context and answers) and Replay; anyone can browse, only an active patron can choose a paid one, and the patron section offers checkout, billing management and device linking. Drafts persist per pairing so leaving for Style or checkout loses nothing; checkout opens in a new tab where the browser allows. Mac and Windows: the overlay draws each tap in its sender's theme; the Tap Appearance window keeps the live preview (a sender's latest tap in the theme they sent it with) with only the free controls; the receiver theme picker, receiver checkout and the support prompt are retired. iPhone: see below.

## Sender patron identity

There are no user accounts. A sender's pairing credentials are each scoped to one recipient inbox, so none of them can own a membership that spans pairings, and an inbox can't own the sender's purchase.

- **SenderPatron** (`apps/server/src/SenderPatron.ts`) is a Durable Object per random patron id with its own SQLite (`apps/server/drizzle-patron`): the identity row, keys, one-time link codes, signed billing facts and one checkout reservation. It knows nothing about inboxes or recipients.
- **Patron keys** (`stp1.<patronId>.<keyId>.<secret>`, `formatPatronKey`) are random bearer secrets held by the sender's own browser or app; only their SHA-256 is stored. Four segments, so a key never parses as a pairing credential or invite and vice versa. Possession of a live key is the only proof of membership: a buyer's email, a Creem customer/subscription id, a pairing credential or a forwarded invite proves nothing.
- **Endpoints.** `POST /v1/patrons` (unauthenticated, rate-limited per IP) creates an identity and its first key; `GET /v1/patrons/me`, `POST /v1/patrons/me/checkout`, `POST /v1/patrons/me/manage`, `POST /v1/patrons/me/link-codes`, `DELETE /v1/patrons/me/key` use the key (`PatronAuthorization`). `POST /v1/patrons/link` redeems a link code for a new key.
- **More devices.** A 15-minute, one-time link code from an existing key adds another of the sender's browsers or phones; at most 10 live keys per identity. One membership then covers every pairing on every linked device.
- **Recovery is unavailable if every key is lost.** Support can help with billing/cancellation/refunds, but cannot currently restore a lost patron identity: neither operator key-issuance tooling nor a supported buyer-authentication handoff is built. Merchant-authenticated Creem lookup/portal generation can retrieve a customer by email or id; that does not authenticate the person requesting recovery. Never reassign a subscription or issue a key from supplied email/customer/subscription ids, and never re-charge to recover. Safari may clear site data for sites not used in 7 days unless added to the Home Screen, so linking a second device is the practical backup. **Decision for the owner:** whether to add self-service recovery (for example email magic links via an email provider, or Creem's customer portal identity), which would need provider setup not authorized in this change.
- **Sharing.** A patron could hand a link code to someone else; the 10-key cap bounds that, as with any shared login.

## Checkout and lifecycle

New checkouts carry `metadata.patron_id` and are created only from `POST /v1/patrons/me/checkout`. The webhook routes each subscription fact by its own metadata: `patron_id` to that SenderPatron, `inbox_id` (historical receiver subscriptions) to that Inbox, where it can still be managed, canceled and refunded but grants nothing. Facts are never copied between subjects, and no historical purchase is reassigned to a sender or auto-enrolled.

The fold, idempotent fact ledger, refund-by-transaction handling, checkout reservation (one per billing subject, shared by that sender's devices), provider-status reuse of pending checkouts and uncertain-creation hold are unchanged and described below; they now apply per sender identity.

## Compatibility and storage

- Every device snapshot retains the original plan shape and emits `status: paid`, even for an expired/refunded/nonpaying inbox. This is a compatibility value so older desktops do not present a paywall or pause messages. It is not purchase evidence. Actual legacy `paid_at`, `order_id`, `purchase_email` and trial dates are preserved separately. Existing buyers are thanked and not auto-enrolled.
- `POST /v1/checkout` no longer sells anything. Authenticated devices get a Conflict explaining free use. An old “Unlock for $5” button can never silently open the annual checkout.
- `POST /v1/patron/checkout` (the receiver-owned annual checkout) now answers devices with a Conflict explaining that support belongs to senders; senders get Unauthorized as before. `POST /v1/patron/prompt` always answers `{ show: false }`. `POST /v1/patron/manage` still opens the portal for a historical receiver subscription. The receiver snapshot's `patron` reflects only that historical subscription, with `canSubscribe: false`.
- Web outboxes retire persisted billing-pause banners while preserving failed drafts and requiring a deliberate retry; old messages are never auto-sent.
- `patron` is an additive optional field on device snapshots; sender snapshots never expose billing state. Swift and Rust tolerate absent/malformed optional fields from old/new servers. The server remains authoritative.
- The additive `20261021152554_free_core_patrons` migration stores event facts, checkout reservations, legacy refund tombstones and prompt history. It does not rewrite old purchase columns or delete trials. New setup ignores the fingerprint older clients still send; no new TrialLedger claims are made.
- Membership follows the sender's patron identity, across their pairings and linked devices (see "Sender patron identity"). All-keys-lost recovery is unavailable; support can handle billing but cannot yet restore membership. Do not pay again to recover.
- The `20261021173050_sender_themes` Inbox migration is additive: `taps.theme` and `appearance.sender_themes`, each with a named CHECK, no table rebuild. The SenderPatron's `drizzle-patron` migrations create its own tables.

## Provider lifecycle details

The installed official `creem` SDK is 1.13.0. Product retrieval must confirm an active USD 2400 recurring `every-year` product with no trial or metered usage before creation. Legacy and patron product IDs are distinct configuration values. The sender's patron id is checkout metadata (`patron_id`; historically the inbox id, `inbox_id`), copied by Creem to subscription metadata. `request_id` is correlation, not assumed provider idempotency.

A durable transaction reserves one checkout per billing subject (the sender's patron identity), shared across that sender's devices. Pending checkouts reuse their URL. The provider's `expired` status permits a new attempt; processing/completed checkout status waits for the webhook. A network failure during creation leaves a reservation with no URL, because retrying an uncertain request could create a second subscription. SDK automatic retries are disabled. An operator must reconcile this exceptional case: find the checkout by the reservation's request ID in Creem, save its ID/URL if it exists, or clear that exact reservation only after confirming no payable checkout exists. Do not clear a reservation just because time has elapsed.

`/v1/webhooks/creem` verifies the raw body with the configured signing secret before decoding. Invalid signatures get 400; storage/provider/recognized-payload failures get 500 for retry. Unrelated products/events get 200 without mutation. Bare subscription IDs on refunds and missing subscription metadata are resolved through supported subscription retrieval, not guessed from URLs.

The immutable fact ledger deduplicates event IDs. It folds by provider event time with conservative tie ordering, independently for each subscription:

- `subscription.paid` alone extends the paid period, on first payment or renewal. `checkout.completed` is not proof of an annual payment; it still handles outstanding historical one-time checkouts for the legacy product.
- `subscription.active` synchronizes state without extending paid time.
- `subscription.scheduled_cancel` and `subscription.canceled` stop renewal UI while patron status remains through the paid period. It ends exactly at the paid boundary, even without a final webhook. Core messaging continues.
- `subscription.past_due`, `subscription.unpaid` and `subscription.expired` never extend paid time. Payment recovery uses the customer portal; a later paid event recovers support. `subscription.paused` suppresses active patron status.
- A succeeded `refund.created` removes the corresponding transaction's paid period, including a partial refund. It cannot revoke a later paid renewal or resurrect a refunded payment when delivered out of order. Refunds do not automatically cancel future renewal: manage/cancel that subscription too.
- Legacy refunds leave a durable order tombstone, so late purchase retries cannot restore the refunded purchase marker. No refund affects free-core access.

`POST /v1/patrons/me/manage` authenticates the patron key (and, for historical receiver subscriptions, `POST /v1/patron/manage` a device) and generates Creem's hosted customer portal using that subject's stored customer ID. Creem's current portal docs say portal cancellation stops the subscription immediately; Shouldertap retains patron status through the paid period. The code also accepts scheduled cancellation events. Both surfaces describe canceling renewal and keeping the paid period. Active/recovering subscriptions must be managed before starting another; a completed cancellation permits a fresh annual checkout.

## Promotion policy

The theme a recipient sees on a patron's tap is the only social discovery: no ads, nags, branding paragraphs, watermarks or badges in a received overlay. Recipients' Mac and Windows menus have a quiet, collapsed "Patron themes" note explaining that senders choose styles; there is no automatic prompt anywhere. The earlier Mac recipient support prompt is retired (its history columns are kept, no longer written). Senders find the offer only by opening Style in the web sender.

## iPhone purchase boundary and review

Rechecked October 21, 2026, now that the paid benefit lives in the sending app. App Review Guideline 3.1.1 requires in-app purchase to unlock features or functionality within an app; 3.1.3(b) (multiplatform services) lets an app offer features bought elsewhere only if they are also available as in-app purchases. The United States storefront exception in 3.1.1(a) covers buttons and links to other purchase methods; whether it also lets an iPhone app unlock a web-bought feature without offering it through IAP is not something this change assumes. So the native iPhone sender sends every tap in Default, has no theme picker or preview, and never sends a patron key; nothing in it is unlocked by a web purchase. The linked-iPhone inbox view no longer offers checkout; on the US storefront only (StoreKit `Storefront.current`, never locale or IP) it keeps "Manage or cancel earlier support" for a historical receiver subscription. Help now shows the website Support link only after StoreKit confirms the US storefront; unknown/non-US storefronts get an email-support link instead. It follows Storefront updates and fails closed while loading. This addresses the direct purchase-page exposure at the UI code boundary; App Review remains external.

To bring themes to the native sender: a StoreKit auto-renewable subscription for the same entitlement (App Store Connect product, price tier, review screenshots), server-side App Store Server API/Notifications V2 verification folding into the same SenderPatron (with `originalTransactionId` as the subject's StoreKit link), Restore Purchases mapping to a patron key, native preview renderers (the Mac `ThemeViews` are AppKit-hosted SwiftUI and would need an iOS build), and a policy decision on whether web-bought memberships may unlock on iPhone. None of that is built, and no approval is implied.

App Review remains an external gate: explain the optional recurring support, free functionality, absence of in-app unlocks, annual billing and server-first rollout in review notes.

## Integrated phone-first rollout boundary

This integration keeps the sender-owned model above. An iPhone may create its recipient inbox and receive/answer without a computer; native iPhone sending remains Default-only. iPhone UI is status-only and exposes no external checkout/management or purchase-page links. The earlier USA-storefront links described in historical verification are not enabled in this integration.

New **sender** checkout is fail-closed: `PATRON_CHECKOUT_ENABLED` defaults false and is checked after key authentication, before product retrieval, checkout reservation or provider creation. Existing subscription management and signed webhooks remain available. Live merchant approval and sender-model product copy must be resolved before enabling signup. No existing production product ID is treated as approval. Core messages never depend on this gate.
